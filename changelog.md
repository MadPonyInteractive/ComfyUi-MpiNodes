# Version: V1.2.8
- MpiBrushTrain - added (trains a Gaussian splat from a COLMAP dataset with Brush, Apache-2.0, and returns the exported .ply path. The binary is fetched per-platform on first use and SHA-256 verified against a checksum pinned in source rather than fetched beside the payload; brush_path overrides the whole thing so an installer that manages the binary never reaches the network. Progress is polled from the export directory, not parsed from stdout - Brush writes zero bytes when it is not a TTY, so there is no N/M Steps line to read and a silent run must not be mistaken for a hung one. Stages a single-model root before training because a SplatKit dataset carries four COLMAP models, the two under _spheresfm_work/ using camera model 11 (SPHERE), which Brush picks between nondeterministically and then fails on with Invalid camera model; the images are hardlinked, since the datasets run to double-digit GB. Interrupting the prompt kills the trainer - a bake runs for tens of minutes)
- MpiVideoSamplingPreview - trims the trailing guide latents (LTXVAddGuide's `keyframe_idxs`) before decoding, so the preview shows the clip and not the user's own conditioning frames pasted onto the tail. Only reachable on LTX: H3 has no guide node, which is why the previewer shipped without it. No socket change - the count is read off the positive cond inside the OUTER_SAMPLE wrapper
- MpiH3MaskedPrefix - added (continue a MiniMax H3 clip by writing its encoded tail into the front of the target latent and masking that region out of sampling, so nothing is regenerated and nothing has to be trimmed. context_frames is snapped DOWN to 39 / 90 / 141 ...: the only lengths that sit on H3's 17k+5 video grid AND divide by 3, so audio's 40 Hz clock lands on a whole step too - an off-grid value does not raise, it drifts the audio against the picture and starts the continuation from a moment that never happened, so the snap is reported rather than assumed. The noise mask is built at the latent's own resolution on purpose: core's reshape_mask INTERPOLATES a mask that does not match, which would smear the one boundary that has to stay hard. Measured on the bench at PSNR 38 dB against the source over the preserved head - a VAE round trip, not a regeneration. Known open defect: the tail carries a sparkle artifact that a zero-content prefix does NOT produce, so it comes from the written content and not from the mask)
- MpiH3EncodeAV - added (encode a clip and its soundtrack into ONE MiniMax H3 AV latent, which is what MpiH3MaskedPrefix takes as its context. Core encodes the two streams separately - VAEEncode + VAEEncodeAudio - and exposes no way to join them, so without this the only route to a joint latent is a third-party fork that monkey-patches two ComfyUI internals at import time. Verified bit-identical to that fork's node on the same seed and clip. Batch 1 only, matching H3 itself; a second item would silently pair the wrong soundtrack to the picture rather than fail)
- MpiLoadVideo - added optional force_rate (default 0 = source rate): ffmpeg resamples to the target frame rate as an output option of the decode pass the node already makes, so there is no second pass and no interpolation model to download, and fps / frame_count / duration are then all reported at the forced rate. It is `optional`, not `required`, on purpose: a required input absent from an API-format prompt is a hard required_input_missing error, and every workflow already calling this node omits it. Exists because nothing on the engine resamples an IMAGE batch by frame rate - VHS_SelectEveryNthImage only decimates by an integer and FrameInterpolate needs RIFE - so a clip generated at one rate and a source loaded at another play at different speeds once joined
- MpiBrushTrain - added optional max_resolution (default 2048), passed through as Brush's --max-resolution. Brush caches one decoded u8 RGB copy of EVERY training view in host RAM, lazily, and its own default caps that at 1920, so the widget is both the RAM knob and a correctness fix: the cache is N_views * min(face_size, max_resolution)^2 * 3 bytes - measured at 7.93 GB over 984 faces at 87% coverage, ~10 GB full at 1920, ~11.5 GB at 2048 and 4.5 GB at 1280 - while a dual-res chain rendering 2048 faces had its top 6% silently thrown away by a ceiling nobody chose, at exactly the stage dual-res exists to sharpen. VRAM is unaffected, flat at ~4.7 GB. Appended as optional, so saved workflows keep their sockets and get 2048 by default
- MpiH3EncodeAV - added optional mask + mask_start / mask_end, which turns it into the H3 INPAINTING encode. The mask is packed onto the video latent's own grid by union of the frames each latent step really carries, not interpolated: H3's VAE packs on a period-5 cycle (1, 4, 4, 4, 4 frames per step), so core's reshape_mask - and LanPaint's own AV Encode - snap each step to a SINGLE picked frame, which drops a mask covering only a few frames with no error at all. The spatial reduction is a max too, so a thin mask is not averaged below the strength it exists to carry. The mask may cover the whole clip or just a RANGE of it, which is what a segmenter run over part of the clip returns; mask_start says which clip frame its first frame lands on, and a mask running past the end raises rather than inpainting a different moment and returning a clean render of the wrong thing. The audio half is masked all-keep and sized off the encoded audio latent, so nothing has to supply a frame count or a frame rate to get it right. Exists because the only other route to H3 inpainting is LanPaint's AV Encode, whose audio_mask is a 1-D [F] tensor at video frame rate that ONLY its interactive video mask editor produces - no core node emits a 1-D MASK - and which takes a VIDEO, so the whole path is unreachable from a host app driving IMAGE + AUDIO. Appended as optional and unconnected it is byte-identical to before
- MpiH3DecodeAV - added (decode the video half of an H3 AV latent and composite it back into the original frames through the same mask, which finishes the job MpiH3EncodeAV starts). Outside the mask the result is the ORIGINAL pixel rather than a VAE round trip of it, so an inpaint does not quietly soften the whole frame the way a plain decode does. feather is dilate-then-Gaussian, transcribed from LanPaint's blend_overlap and verified equal to it to 8e-07 in the interior: dilating BEFORE the blur is what puts the whole ramp outside the mask that was drawn, so the inpainted content holds full strength at its own edge - a blur on its own leaves that edge at roughly half and reads as the inpaint not having taken. One deliberate divergence: replicate rather than zero padding, so a mask touching the frame border - a subject walking out of shot - is not faded away there, where LanPaint drops it to 0.58. The Gaussian is applied separably, so the cost is 2k per pixel rather than k*k. There is no audio cross-fade counterpart because nothing is spliced into the soundtrack: the audio half is deliberately NOT decoded and there is no audio_vae input; the encode masks audio all-keep, so the soundtrack coming back is the one that went in, and the original AUDIO is wired straight past this node to the combine - a round trip through the audio VAE could only make it worse. A decode whose frame count does not match the originals raises and names H3's 17k+5 grid, and a video-only latent raises instead of half-decoding
- MpiAudioRange + MpiImageSplice - added (the two halves of windowed video work: cut a soundtrack to a FRAME range, and write a run of frames back into a longer clip). Exists because masking a few frames of a video model does not make it cheaper - the sampler denoises the whole latent every step whatever the mask says, and LanPaint multiplies that by its inner NumSteps - so the only real lever is feeding it a shorter clip and splicing the result back in pixel space. MpiAudioRange takes the same inclusive start/end as MpiListRange so one pair of numbers windows picture and sound together: cutting the frames and leaving the audio whole hands an audio-video model a soundtrack that does not line up with the picture, and nothing downstream can notice, because every tensor is still valid and the result is merely conditioned on the wrong moment. The splice needs no blending at the window edge because MpiH3DecodeAV already returns the original pixel outside the mask, so the boundary is bit-identical; a mismatched canvas or a patch running past the end raises rather than landing as a clip that plays but is wrong
- MpiH3EncodeAV - a mask on a frame count off H3 17k+5 grid now RAISES at encode, naming the nearest valid count, instead of surfacing later as a mask-overhang error after a full sample has been paid for. A 6-frame clip packs to 5 and the sixth frame is dropped by the VAE with no complaint, which then reads as the mask covering the wrong range. Only checked when a mask is connected: the context path (MpiH3MaskedPrefix) deliberately accepts off-grid clips, and only inpainting needs the clip to survive the round trip frame-for-frame

# Version: V1.2.9
- MpiMaskSquareBbox - takes the box from the UNION of every frame in the batch and returns the filled square for EVERY frame, instead of reading frame 0 and returning a single mask. The old output was indistinguishable from a deliberate one-frame range: fed to MpiH3EncodeAV it inpainted frame 0 and silently kept the other 123, because place_mask zero-fills whatever the mask does not cover. Unioning also keeps the composite seam STILL - a per-frame box crawls, and a crawling seam is far more visible in motion than a fixed one. A single-image mask is unaffected: one frame in, one out
- MpiH3EncodeAV / MpiH3DecodeAV - a single-frame mask at mask_start 0 now covers the WHOLE clip rather than frame 0 alone. One mask for a clip has only one sensible reading, and the other one - inpaint the first frame, keep the rest - is a silent no-op that no caller wants and nothing downstream can detect. A mask placed at a non-zero mask_start is a deliberate range and is left exactly as it was
- MpiH3DecodeAV - the feather dilate is now two 1-D max pools instead of one k*k, which is bit-identical and 26.7x faster measured at k=61 on 1536x640 (179s -> 6.7s over a 124-frame clip, on CPU). Max is separable exactly as the Gaussian beside it already was; only the Gaussian had been done that way, so a wide feather cost 3721 comparisons per pixel per frame and read as a hung node rather than a slow one - and it cannot be interrupted, because ComfyUI checks between nodes and sampler steps, never inside one torch op
- MpiH3DecodeAV - feather is now min 1 rather than min 0, so its step-2 grid lands on the ODD numbers the kernel actually uses. With min 0 every reachable value was even while the code centres the kernel with `feather | 1`, so the default 11 sat off its own grid: one press of an arrow snapped it to 10 or 12 and nothing could ever get back to 11. 1 is the hard cut, exactly as 0 was - the feather block is skipped for both
- MpiInpaintHeal - the ring dilate and the box blur are now separable, taking the node from ~710s to ~38s on a 124-frame 1536x640 clip at the default ring_px 31 (the dilate alone measured 25.1x, bit-identical). `_ring_of` was a single 63x63 max pool per frame - 3969 comparisons per pixel - and `_box_blur` a k*k avg pool, even though `_gaussian_feather`'s own docstring already called the box passes separable. Both are separable kernels, so the cost is 2k rather than k*k and the result is unchanged. This is the same defect the MpiH3DecodeAV feather had: on a video it does not read as a slow node, it reads as a hung one, and it cannot be interrupted because ComfyUI only checks between nodes and sampler steps
- MpiH3DecodeAV - added optional mask_mode (default `per-frame`, byte-identical to before). `as sampled` composites through the mask the MODEL was given rather than the one you drew: pack_video_mask quantises to the latent grid and unions the frames each step packs, and the DiT pools again with amax over its 2x2 patch, so on a 1536x640 clip the model sees 48x20 mask cells smeared over ~4 frames each. Keeping only the thin per-frame mask out of that wide repaint puts the seam INSIDE the region the model worked to, which is exactly where a seam shows - the drawn mask and the painted region are different shapes and no amount of feather reconciles them. Measured +27% area kept on a 124-frame clip, always a superset of the per-frame mask, 0.24s. Appended as optional, so saved workflows keep their sockets and their behaviour
