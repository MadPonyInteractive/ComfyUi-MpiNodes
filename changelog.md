- MpiH3EncodeAV - added optional mask + mask_start / mask_end, which turns it into the H3 INPAINTING encode. The mask is packed onto the video latent's own grid by union of the frames each latent step really carries, not interpolated: H3's VAE packs on a period-5 cycle (1, 4, 4, 4, 4 frames per step), so core's reshape_mask - and LanPaint's own AV Encode - snap each step to a SINGLE picked frame, which drops a mask covering only a few frames with no error at all. The spatial reduction is a max too, so a thin mask is not averaged below the strength it exists to carry. The mask may cover the whole clip or just a RANGE of it, which is what a segmenter run over part of the clip returns; mask_start says which clip frame its first frame lands on, and a mask running past the end raises rather than inpainting a different moment and returning a clean render of the wrong thing. The audio half is masked all-keep and sized off the encoded audio latent, so nothing has to supply a frame count or a frame rate to get it right. Exists because the only other route to H3 inpainting is LanPaint's AV Encode, whose audio_mask is a 1-D [F] tensor at video frame rate that ONLY its interactive video mask editor produces - no core node emits a 1-D MASK - and which takes a VIDEO, so the whole path is unreachable from a host app driving IMAGE + AUDIO. Appended as optional and unconnected it is byte-identical to before
- MpiH3DecodeAV - added (decode the video half of an H3 AV latent and composite it back into the original frames through the same mask, which finishes the job MpiH3EncodeAV starts). Outside the mask the result is the ORIGINAL pixel rather than a VAE round trip of it, so an inpaint does not quietly soften the whole frame the way a plain decode does. feather is dilate-then-Gaussian, transcribed from LanPaint's blend_overlap and verified equal to it to 8e-07 in the interior: dilating BEFORE the blur is what puts the whole ramp outside the mask that was drawn, so the inpainted content holds full strength at its own edge - a blur on its own leaves that edge at roughly half and reads as the inpaint not having taken. One deliberate divergence: replicate rather than zero padding, so a mask touching the frame border - a subject walking out of shot - is not faded away there, where LanPaint drops it to 0.58. The Gaussian is applied separably, so the cost is 2k per pixel rather than k*k. There is no audio cross-fade counterpart because nothing is spliced into the soundtrack: the audio half is deliberately NOT decoded and there is no audio_vae input; the encode masks audio all-keep, so the soundtrack coming back is the one that went in, and the original AUDIO is wired straight past this node to the combine - a round trip through the audio VAE could only make it worse. A decode whose frame count does not match the originals raises and names H3's 17k+5 grid, and a video-only latent raises instead of half-decoding
- MpiAudioRange + MpiImageSplice - added (the two halves of windowed video work: cut a soundtrack to a FRAME range, and write a run of frames back into a longer clip). Exists because masking a few frames of a video model does not make it cheaper - the sampler denoises the whole latent every step whatever the mask says, and LanPaint multiplies that by its inner NumSteps - so the only real lever is feeding it a shorter clip and splicing the result back in pixel space. MpiAudioRange takes the same inclusive start/end as MpiListRange so one pair of numbers windows picture and sound together: cutting the frames and leaving the audio whole hands an audio-video model a soundtrack that does not line up with the picture, and nothing downstream can notice, because every tensor is still valid and the result is merely conditioned on the wrong moment. The splice needs no blending at the window edge because MpiH3DecodeAV already returns the original pixel outside the mask, so the boundary is bit-identical; a mismatched canvas or a patch running past the end raises rather than landing as a clip that plays but is wrong
- MpiH3EncodeAV - a mask on a frame count off H3 17k+5 grid now RAISES at encode, naming the nearest valid count, instead of surfacing later as a mask-overhang error after a full sample has been paid for. Only checked when a mask is connected: the context path (MpiH3MaskedPrefix) deliberately accepts off-grid clips, and only inpainting needs the clip to survive the round trip frame-for-frame

# Version: V1.2.9
- MpiMaskSquareBbox - takes the box from the UNION of every frame in the batch and returns the filled square for EVERY frame, instead of reading frame 0 and returning a single mask. The old output was indistinguishable from a deliberate one-frame range: fed to MpiH3EncodeAV it inpainted frame 0 and silently kept the other 123, because place_mask zero-fills whatever the mask does not cover. Unioning also keeps the composite seam STILL - a per-frame box crawls, and a crawling seam is far more visible in motion than a fixed one. A single-image mask is unaffected: one frame in, one out
- MpiH3EncodeAV / MpiH3DecodeAV - a single-frame mask at mask_start 0 now covers the WHOLE clip rather than frame 0 alone. One mask for a clip has only one sensible reading, and the other one - inpaint the first frame, keep the rest - is a silent no-op that no caller wants and nothing downstream can detect. A mask placed at a non-zero mask_start is a deliberate range and is left exactly as it was
- MpiH3DecodeAV - the feather dilate is now two 1-D max pools instead of one k*k, which is bit-identical and 26.7x faster measured at k=61 on 1536x640 (179s -> 6.7s over a 124-frame clip, on CPU). Max is separable exactly as the Gaussian beside it already was; only the Gaussian had been done that way, so a wide feather cost 3721 comparisons per pixel per frame and read as a hung node rather than a slow one - and it cannot be interrupted, because ComfyUI checks between nodes and sampler steps, never inside one torch op
- MpiH3DecodeAV - feather is now min 1 rather than min 0, so its step-2 grid lands on the ODD numbers the kernel actually uses. With min 0 every reachable value was even while the code centres the kernel with `feather | 1`, so the default 11 sat off its own grid: one press of an arrow snapped it to 10 or 12 and nothing could ever get back to 11. 1 is the hard cut, exactly as 0 was - the feather block is skipped for both
- MpiInpaintHeal - the ring dilate and the box blur are now separable, taking the node from ~710s to ~38s on a 124-frame 1536x640 clip at the default ring_px 31 (the dilate alone measured 25.1x, bit-identical). `_ring_of` was a single 63x63 max pool per frame - 3969 comparisons per pixel - and `_box_blur` a k*k avg pool, even though `_gaussian_feather`'s own docstring already called the box passes separable. Both are separable kernels, so the cost is 2k rather than k*k and the result is unchanged. This is the same defect the MpiH3DecodeAV feather had: on a video it does not read as a slow node, it reads as a hung one, and it cannot be interrupted because ComfyUI only checks between nodes and sampler steps
- MpiH3DecodeAV - added optional mask_mode (default `per-frame`, byte-identical to before). `as sampled` composites through the mask the MODEL was given rather than the one you drew: pack_video_mask quantises to the latent grid and unions the frames each step packs, and the DiT pools again with amax over its 2x2 patch, so on a 1536x640 clip the model sees 48x20 mask cells smeared over ~4 frames each. Keeping only the thin per-frame mask out of that wide repaint puts the seam INSIDE the region the model worked to, which is exactly where a seam shows - the drawn mask and the painted region are different shapes and no amount of feather reconciles them. Measured +27% area kept on a 124-frame clip, always a superset of the per-frame mask, 0.24s. Appended as optional, so saved workflows keep their sockets and their behaviour
- MpiH3EncodeAV - added optional audio_start / audio_end, which opens a window in the SOUNDTRACK the way the mask opens one in the picture, plus a second `info` output reporting what was actually masked on both halves. The audio was masked all-keep by a deliberate scoping call; unmasking a time range is context-aware foley, and it is the thing a standalone foley model cannot do - that generates in isolation from a silent clip, while H3 hears the rest of the track as unmasked context, so the generated window matches the room, the mic and the ambience, and is in sync by construction because one model produces both halves. The range is given in FRAMES and snapped OUTWARDS to a multiple of 3: audio runs on a 40 Hz clock against 24 fps picture, so a frame boundary is a whole audio step only every third frame, and an off-grid edge raises nowhere - it lands the seam a fraction of a step out and drifts the sound against the picture, the same silent failure as an off-grid frame count, which is why the snap is reported rather than assumed. audio_end -1 takes the audio latent whole instead of computing an end from the frame count, because a clip length on the 17k+5 grid is never a multiple of 3 and its last step is a fraction. The two masks are independent, so an audio window with NO picture mask regenerates sound over untouched video - the pure foley case - and the picture half is then sized off the video latent as all-keep. The limitation is structural and shapes how the widget is used: an audio mask selects a TIME range, not a SOURCE, because audio sums every source into the same samples, so the window regenerates dialogue, room tone and footsteps together; MpiH3DecodeAV's audio_mode is the layering answer. Appended as optional with audio_end defaulting to 0, so unconnected it is byte-identical to before
- MpiH3DecodeAV - added optional audio_vae / audio / audio_start / audio_end / audio_mode / audio_crossfade and a second AUDIO output, so the node finishes the audio half of the job as well as the picture half. It shipped without them deliberately - nothing was spliced into the soundtrack, so there was no audio seam to hide - and that held exactly as long as the encode masked audio all-keep, which an audio window ends. Outside the window the sample is the ORIGINAL, not a VAE round trip of it, matching what the picture half already promised. The decode is taken RAW rather than through core's vae_decode_audio, which divides by its own standard deviation to keep a bare decode from clipping: that lands it in a different loudness domain from the waveform it is about to be spliced into, and here the kept audio is the reference, so raw is what makes the levels line up on their own. audio_crossfade is feather's counterpart - equal power (sqrt) rather than linear, because the generated window is a different take and two uncorrelated sides through a linear pair dip about 3 dB through the middle of the crossover - and the ramp sits INSIDE the window, so the kept soundtrack is never touched. Without it a splice clicks, and a click is the one artefact an audio edit cannot hide. audio_mode `mix` sums the generated window UNDER the original instead of replacing it, which is the only way to LAYER a sound onto a track that already carries a performance: the mask selects a time range and not a source, so replace throws the original dialogue away along with the silence it was meant to fill. A soundtrack shorter than the window raises rather than being truncated silently. With no audio_vae, or audio_end at 0, the audio input is passed straight through, so a picture-only inpaint keeps its old wiring and its old result
- MpiAudioSplice - added (write a run of audio back into a longer soundtrack at a FRAME offset, taking the same inclusive start MpiListRange and MpiAudioRange take, so the number that CUT a window writes it back). It is the inverse MpiAudioRange shipped without and the sound half of what MpiImageSplice does for picture: windowed work on an audio-video model cuts both streams, generates, and has to splice both back, and until now only the picture had a way home. Without it a regenerated soundtrack stays window-length while the picture returns full-length, which reads as a video whose sound stops early rather than as a wiring mistake - VHS writes the short track without complaint. The crossfade is MpiH3DecodeAV's own splice_audio, so there is one implementation of the equal-power fade rather than two that can drift; the patch is laid into a full-length buffer first because that function indexes both sides in the same coordinates. A patch running past the end of the track raises and says by how many samples, naming the two things that actually cause it - a start that names a different window, or a patch from a different clip - rather than landing silently short. A mono patch is expanded to a stereo track instead of broadcasting into a crash, and a cut spliced straight back is a bit-exact no-op
- MpiH3DecodeAV - added optional audio_gain (default 1.0, so unchanged when untouched), and the mix fade is now linear rather than equal power. Both come from the first real listen: the model's take comes back at whatever level it decided on, which is rarely the level of the track it has to sit in, so under `replace` the window jumped out louder than what surrounded it. gain is the trim for that. Under `mix` it matters more than as a nicety - the mask selects a time range and not a source, so the generated window carries the model's own re-invented score and ambience alongside the sound that was wanted, and summing at full strength doubles them; around 0.3 is where a new layer starts to sit under an existing track rather than fight it. The fade curve now follows the mode because the two are not the same operation: `replace` crosses between two takes of one moment, which do not correlate, so equal power is right and holds level through the crossover, while `mix` fades a layer in over an original that keeps playing underneath, where equal power would start the layer at 71% of its level on the very first sample - a click of exactly the kind the crossfade exists to remove
- MpiH3EncodeAV / MpiH3DecodeAV - added optional audio_ranges (default empty, so unchanged when untouched): several DISJOINT stretches of a clip regenerated in one pass, written as `0-10, 40-50, 90-100`, start inclusive and end exclusive to match audio_start/audio_end on the same node. A bare number is one frame and an end of -1 runs to the clip end. This is the capability LanPaint's interactive video mask editor has and no core node exposes; it is spelled as TEXT rather than as the 1-D [F] MASK LanPaint consumes because nothing emits that shape - not core, not a segmenter, and not a host app driving the graph over HTTP. Ranges are snapped outwards individually and then MERGED where they overlap or touch: two ranges three frames apart can collide once both are snapped to the 40 Hz grid, and splicing them separately would ramp the second range's crossfade into audio the first had already written, fading into material that is not the original. Both nodes resolve the spec through one shared helper so they cannot disagree about which input is in charge - a disagreement would mask one stretch and splice a different one with every tensor still valid. The encode's `info` output now also reports how many audio steps were left UNMASKED, and says so explicitly when the answer is none: the model matches room, mic and ambience by listening to what was not masked, so a clip whose audio is entirely masked has nothing to match and returns its own score at its own level. That is legitimate - it is just not foley - so it is reported rather than raised
- MpiH3ImageToVideo - added (MiniMax H3 image-to-video conditioning that accepts an EMPTY first_frame / last_frame, so one graph covers t2va, first-frame, last-frame and first+last). Core's MiniMaxH3ImageToVideo already skips a keyframe that arrives as None, but nothing can send None down a connected link, so covering the four cases cost a pre-authored branch each - the fl2va workflow was carrying four copies of the core node behind has_img1 / has_img2 / is_i2v booleans and four packers, and every future change had to be made four times. Empty is not guessed from content: it is None or the loaders' 1x1 block_if_empty-OFF sentinel, the same rule MpiH3References already uses, so a genuinely black anchor frame reports its true size and passes through. The conditioning is DELEGATED to core's execute rather than copied, for the same reason the reference node delegates - its tensor maths moves with ComfyUI and a private copy would drift silently. The second reason it exists is the H3 latent upscaler: a refine pass on an upscaled latent needs conditioning rebuilt at the new dimensions, because MiniMaxH3ImageToVideo VAE-encodes the keyframe at the FIRST stage's width/height while PackedLayout sizes its cond rows off the TARGET grid, so a 2x upscale raises 'value tensor of shape [209, 96] cannot be broadcast to indexing result of shape [836, 96]' inside SamplerCustomAdvanced - 4x the tokens, the anchor still at 1x. Building that second conditioning previously meant duplicating the whole lattice

# Version: V1.2.10
- MpiH3ImageToVideo - both keyframes are now cover-cropped to the canvas before the conditioning is delegated, so a source whose aspect does not match the target is CROPPED rather than squashed. Core is asymmetric about this and neither half is what a host app wants: MiniMaxH3ImageToVideo resizes first_frame with crop='disabled' - a plain stretch, commented "geometry anchor" - while last_frame gets 'center'. So a 9:16 photo asked for on a 1:1 canvas came back visibly squashed, and when BOTH frames were supplied they were conformed by two different rules and disagreed with each other, which reads as the model drifting between the ends of the shot rather than as a resize bug. Core has no source-patch mechanism, so the conform has to happen upstream of it; handing it images already at the canvas size turns its own resize into a no-op, which keeps ONE resize in the pipeline instead of two. Crop and not pad, on the user's call: letterbox bars would be baked into frame 0 and H3 animates them as scenery - the model has no notion that part of its anchor is furniture. An image already at the target size is returned untouched rather than sent through a pointless lanczos round trip, and the crop MODE is pinned by the module self-check, because a regression to 'disabled' is invisible in the graph and shows up only as a squashed frame 0.

# Version: V1.2.11
- MpiWindowedSampler - added (SamplerCustomAdvanced run over overlapping temporal windows, cross-faded). A video DiT's attention cost scales with T x H x W, so the same settings succeed at one duration and OOM at another with nothing else changed: measured on MiniMax H3 at 2K (latent 92x160) on a 16GB card, T=27 samples fine while T=32 and T=37 both die inside comfy_kitchen.prequantize_int8_attention on a 959.88 MiB allocation. That is not tuning - H3's trained minimum is 124 frames, which IS T=37, so the model's SHORTEST trained clip is the one the card cannot refine. Lowering the upscale factor does not reach it either, because stage-2 peak is set by the OUTPUT latent size and not by the factor; 1.5x only moves cost into stage 1 (+79% stage-1 peak, +31% total) and leaves the ceiling exactly where it was. Windowing is sound HERE and would not be for a first-pass generation, because this is a refine: the latent arrives globally coherent, motion and identity and framing already decided upstream, so a short sigma schedule adds local detail and two windows have nothing to disagree about. Noise is generated ONCE for the whole clip and sliced per window rather than generated per window - otherwise the two sides of a seam get different noise and the cross-fade averages two genuinely different denoisings instead of two near-identical ones, which is the difference between a seam you cannot find and one you can. Audio in a joint AV latent is passed through untouched: the refine exists to add spatial detail, and stitching audio across seams puts a discontinuity in the one channel a listener notices immediately. The model stays loaded across windows deliberately - unloading between them re-streams the whole DiT over PCIe once per window and costs far more than the sampling it protects. A clip that already fits (T <= window) takes the plain single-pass path, so short clips are unchanged
- MpiClearVramEnd - added (MpiClearVram as a terminal node with no output). Clearing VRAM properly needs one per terminal branch, because the node only runs on branches that actually execute - a single clear hung off the preview branch leaves models resident for every other branch and nothing reports it, the symptom being an OOM later in the graph with "0 models unloaded" in the log. The pass-through version has to be spliced INTO a branch, so covering three sinks - a latent, a decoded image, a decoded audio - means moving three existing links; this one hangs off the END of a branch and changes nothing downstream because there is no downstream. The trigger input is required and exists only to place the node in execution order: an unconnected sink would run at an arbitrary point, which is the one thing a VRAM clear must not do. The pass-through node is untouched, since shipped workflows reference it
- MpiWindowedSampler - windows are now cut on the model's temporal grid (new frame_grid widget, default 5), and `window` became a CEILING rather than a target. Measured on H3 at 2K, T=37: window 27 (5*5+2) was clean, window 21 (5*3+6) put a BLACK frame at the end of BOTH windows. The blend maths was exonerated first - an identity sampler reconstructs the clip to under 1e-5 across 875 shape combinations - so the cause is the length itself. H3 patchifies time as a 2-frame causal head plus blocks of 5, so a legal latent length is 5k+2 and a legal cut point is a multiple of 5; a window of 21 ends four frames into a block and the padded remainder decodes black. It reads as a seam artefact, which is the wrong place to look. Both the window LENGTH and the stride are now snapped, so windows start on the grid as well as end on it, and snapping the stride can only ever hand out MORE overlap than was asked for. Because the pass count is what costs time and not the window size, the window then shrinks to the smallest legal size that still covers in the same number of passes: at T=37 a ceiling of 27 now plans two 22-frame windows instead of two 27s, which is 44 latent-frames of sampling instead of 54, and the measured per-window time at 21 frames was 6:54 against 9:40 at 27. So the ceiling is now the honest thing to set it to - the largest your card handles - and a generous one costs nothing. frame_grid 1 means the model has no such constraint and gives plain fixed-size windows. Where grid and ceiling disagree the grid wins, because an over-ceiling window risks an OOM while an off-grid one guarantees black frames; the log line reports both numbers
- MpiWindowedSampler - the crossfade now ramps over the frames the windows ACTUALLY share, and both frame widgets moved to VIDEO frames. Snapping the stride to the grid hands out more overlap than was asked for, but the blend was still ramping over the REQUESTED number, so a plan sharing 7 frames crossfaded across 4 of them and hard-cut the other 3. Measured on H3 at T=37: the same seam went from a face visibly becoming two faces, to a trace of distortion at 7 shared frames, to clean at 17. That is the shape of a blend artefact and not a model one - the windows denoise the shared frames independently, so the fade has to be wide enough to hide two valid but different answers, and width is the only lever this architecture has. The widgets are now window_frames and overlap_frames in VIDEO frames, because an OOM is discovered as 'it died at 124 and survived at 90' - nobody measures a latent frame count, so a latent-frame dial cannot be calibrated by the person who hit the wall. The conversion needs no extra widget: H3 packs (1, 4, 4, 4, 4) video frames per latent frame indexed by absolute position mod 5 (MiniMaxH3AV.fix_empty_latent), so `ratio*T - (ratio-1)*ceil(T/grid)` with the model's own temporal_downscale_ratio reproduces ComfyUI's count exactly - checked against its loop for every length to 400, and against both lengths this card has measured (T=37 -> 124, T=22 -> 73). A third `info` STRING output reports the plan in both units, the same way MpiH3EncodeAV reports what it actually masked: the numbers a user types are a ceiling and a minimum, so what they get is never quite what they asked for, and a node that silently reinterprets its own widgets is one nobody can calibrate. frame_grid 1 turns the conversion off and the widgets then count latent frames, which the info output says rather than leaving it to be guessed
- MpiSaveVideo - added a `video_path` STRING output carrying the absolute path of the mp4 it just wrote. The node was OUTPUT_NODE with RETURN_TYPES = (), so nothing could be ordered AFTER the file existed, and that is what forced MpiClearVramEnd onto every terminal branch: a clear can only run on a branch that executes, so covering the video decode, the audio decode and the latent meant three of them, each firing while the user is still waiting. With a path to hang off, one clear at the tail of the save covers the graph, and it runs after the mp4 is on disk - so the several seconds the unload costs land outside render time instead of inside it, which is the whole point. Existing workflows are untouched: an OUTPUT_NODE with no outputs gains a socket nobody was connected to, and the `ui` payload is unchanged so the preview still appears. Absolute rather than bare filename, because the two consumers in this pack - MpiHasAudio and MpiLoadVideo - both take a path, so the saver now feeds them directly instead of the graph rebuilding a path the node already knew. Image graphs need no equivalent: they end on a preview node, which already has an output to trigger from
